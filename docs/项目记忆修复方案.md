# 项目记忆修复方案

> 状态：已定稿（路线 A・瘦身版）・日期：2026-09-23・适用范围：multi-agent 桌面应用（backend + frontend）
> 评审结论：放弃路线 B（只止血、不解决 "全量注入 / 主理人不参考" 结构问题）与路线 C（当前记忆量小、PyInstaller 打包约束下向量方案体积 / 门槛不匹配）；采用路线 A。治理机制（淘汰 / 衰减）延后，LLM 提炼做成配置开关，检索层留可插拔接口（FTS5 → 向量，触发条件出现后再换）。

## 一、背景与问题回顾

当前 "项目记忆" 存储为 `projects.memory` 单个 TEXT 字段（追加式），存在 5 个问题：



| # | 问题                    | 证据                                                                                  |
| - | --------------------- | ----------------------------------------------------------------------------------- |
| 1 | **有标题无内容的空记录**        | 项目「项目 1」两条记忆只有 `### 时间·标题`，正文为空；`_save_project_memory` 对空 merge 结果仍无条件写入            |
| 2 | **标题用原始需求全文**         | `task_description`（可长达 200+ 字）直接当 `### 标题`，POSP 条目即如此                               |
| 3 | **截断无提示、破坏 Markdown** | 单条 600 字、总量 20000 字硬截断，无省略标记；项目「1」第一条正文末尾为 `\|`（表格截断）                               |
| 4 | **主理人不参考记忆**          | 记忆只注入子 Agent（`manager._call_agent`）；主理人 plan/merge 走 `orchestrator._call_agent`，无注入 |
| 5 | **无去重**               | 同一任务重跑会重复追加                                                                         |

## 二、设计参考（主流 Agent 记忆做法）



| 方案                 | 核心思路                                                                                            | 本项目可借鉴点                         |
| ------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------- |
| **Mem0**           | 记忆是 "一等对象"：每条记忆含内容、元数据、评分、时间戳；**提取式**写入（把对话提炼为原子事实，而非原文截断）；**ADD-only**，新旧事实并存、检索时解决冲突；自动防膨胀与衰减 | 条目化存储；用 LLM 提炼关键结论；写后按任务去重 / 更新 |
| **MemGPT / Letta** | **三层记忆**：Core（核心，常驻 Prompt，小）→ Working（工作上下文，近期）→ Archival（归档，外部存储，按需检索）；记忆由 LLM 通过工具自管理        | 分层注入：核心常驻 + 检索召回，杜绝全量灌入         |
| **通用实践**           | 向量检索按需加载，绝不全量进上下文；关系库存原文 + 元数据                                                                  | 轻量检索（SQLite FTS5，零依赖）；总量预算控制    |

## 四、数据模型（新增）



```
CREATE TABLE project\_memories (

&#x20;   id             INTEGER PRIMARY KEY AUTOINCREMENT,

&#x20;   project\_id     INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,

&#x20;   kind           VARCHAR(16)  NOT NULL DEFAULT 'auto',   -- auto=自动沉淀 / manual=手动

&#x20;   title          VARCHAR(120) NOT NULL,                   -- 简短标题，≤60 字

&#x20;   content        TEXT         NOT NULL,                   -- 结论正文（≤600 字/条，可选提炼时 2\~5 条）

&#x20;   tags           VARCHAR(255),                            -- 逗号分隔，预留检索加权

&#x20;   source\_task\_id INTEGER,                                 -- 来源根任务（仅溯源；去重键为 project_id + title）

&#x20;   pinned         BOOLEAN      NOT NULL DEFAULT 0,

&#x20;   created\_at     DATETIME     NOT NULL,

&#x20;   updated\_at     DATETIME     NOT NULL

);

CREATE INDEX ix\_memories\_project ON project\_memories(project\_id, updated\_at DESC);

CREATE INDEX ix\_memories\_task   ON project\_memories(source\_task\_id);

\-- FTS5 全文检索（SQLite ≥3.19 内置，已验证 3.53.1 支持）

\-- 独立表 + trigram 分词：中文按 3-gram 子串命中，1-2 字查询天然不命中（防噪音）

\-- 实现注：不用 content= 外部内容表 —— 其 'delete' 命令实测报 database disk image is malformed

CREATE VIRTUAL TABLE project\_memories\_fts USING fts5(
    title, content, tokenize='trigram'
);
```



* `projects.memory` 字段**保留**为兼容层：迁移完成后置空或存备份，前端不再读写它（迁移脚本负责）。

* 手动编辑的条目 `kind='manual'`，不参与自动摘要覆盖。

* **不做** hit\_count / 淘汰字段 —— 治理机制延后，等数据量真实超出软上限再按需补充。

## 五、写入链路改造（`manager._save_project_memory`）

**现状**：`excerpt = result_text.strip()[:600]` 无条件追加。

**改造后流程**：



1. **空值保护**：`final.strip()` 为空 → 直接 return，不落库（修问题 1）。

2. **内容处理（默认）**：`content = final.strip()`；超过 600 字则截断并追加 `…` 省略标记（修问题 3 的可读性，无 LLM 依赖）。

   **可选（**`MEMORY_LLM_EXTRACT=true`**，默认关）**：复用现有 `build_provider`（主理人模型），用固定提炼 prompt 把 merge 结果压成 2\~5 条要点（每条 ≤200 字）。提炼失败（异常 / 超时 / 空结果）→ 降级为默认截断，不影响落库。

3. **标题规范化**：用根任务 `task.title` 截断 60 字，不再用 `task_description` 全文（修问题 2）。

4. **去重更新**：按「项目 + 标题」查重（标题已截断归一）—— 命中则更新该条 content/source\_task\_id/updated\_at（Mem0 的 update 语义），未命中才新建（修问题 5）。*实现注：同任务重跑会新建根任务 id，不能用 `source_task_id` 做去重键，它仅作溯源。*

5. **FTS5 同步**：写入 / 更新后显式维护 `project_memories_fts`（`INSERT INTO ...` / `DELETE` + `INSERT`），不用触发器，避免隐式行为。

**提炼 prompt 示意（仅开关开启时使用）**：



```
你是记忆整理器。把以下任务交付总结提炼为 2\~5 条可复用的项目结论，

每条一句话（≤200 字），聚焦：做了什么、关键决策/口径、交付物位置、遗留问题。

不要转述过程，不要客套。输出格式：- 结论1\n- 结论2
```

## 六、读取链路改造（注入）

**现状**：`project.memory[:4000]` 全量注入，仅子 Agent。

**改造后**（对齐 Letta 分层）：



1. **核心记忆块（Core）**：`pinned=1` 的条目 + 按 `updated_at` 最近的 5 条，正文合计 ≤1500 字，始终注入。

2. **检索记忆块（Archival）**：用当前任务标题 / 用户消息关键词对 FTS5（trigram）查询，取 Top-5。**门槛**：提取出的关键词 <2 个或 FTS 无命中时，整个检索块不注入（避免噪音）；bm25 仅用于排序、不做绝对阈值（小语料分数趋近 0，阈值会误拦截命中）。

3. **统一注入位置**：

* `manager._call_agent`（子 Agent）—— 改为走新逻辑；

* `orchestrator._call_agent`（主理人 plan/merge）——**新增注入**（修问题 4）。

1. **总量预算**：两个块合计 ≤3000 字，防止 token 膨胀；超过则优先保留核心块。

2. **封装（可插拔）**：抽出 `build_memory_blocks(db, project_id, query=None, backend="fts5") -> str`，两端复用；`backend` 参数预留 `"vector"` 实现 —— 将来启用向量检索只换检索函数，不动存储与注入层。

## 七、容量与维护（瘦身版）



* **软上限**：每项目 1000 条；超限时仅在日志 / 前端提示 "记忆过多，建议清理"，**不自动删除**（淘汰机制延后，等真实超量再补充 hit\_count 与淘汰策略）。

* **无自动降权 / 衰减**：本期不做 90 天降权。

* **手动管理**：前端记忆面板改为条目列表 —— 支持单条编辑 / 置顶 / 删除；置顶（pinned=1）即进核心块。

* **升级触发条件**（启用向量检索 backend="vector"）：记忆条目 >500 / 项目 且 实测关键词检索漏召回（或用户明确要语义问答）。

## 八、存量数据修复（迁移脚本，幂等）



1. 读 `projects.memory`，按 `### ` 正则切分为候选条目。

2. 每条取首行作标题（截断 60 字），其余作正文。

3. **正文为空 → 丢弃**，但**先写日志**（记录项目 id、标题、时间）便于追溯（修掉项目「1」/「项目 1」的空记录）。

4. 正文非空 → 写入 `project_memories`（`kind='auto'`，`source_task_id=NULL`），正文尾部截断标记 `…`；**正文内含&#x20;**`### `**&#x20;的整段保留为一条，不做二次切分**（避免误切项目「1」正文里的 "1.1 交付物清单" 等子标题）。

5. 旧字段备份为 `projects.memory_bak`（或直接清空，取决于评审意见）。

6. 可重复执行：执行前检查目标表是否已有该时间标题条目，有则跳过。

## 九、实施分期



| 阶段                | 内容                                                        | 工作量    | 交付验证             |
| ----------------- | --------------------------------------------------------- | ------ | ---------------- |
| **P1 最小修复**       | 空值保护 + 标题截断 + 按任务去重（仍用大字符串，先止血）                           | 0.5 天  | 重跑一个任务，确认无空记录    |
| **P2 条目化 + 检索**   | 新表 + FTS5 + 迁移脚本 + 分层注入 + 主理人注入 + 前端记忆面板改列表（编辑 / 置顶 / 删除） | 1\~2 天 | 单测 + 手工跑任务看沉淀与注入 |

建议做到 P2：P1 只止血，不解决 "全量注入" 和 "主理人不参考" 两个结构问题。

## 十一、验证清单



* [ ] 空 merge 结果不产生记忆条目（问题 1）

* [ ] 记忆标题 ≤60 字、无需求全文（问题 2）

* [ ] 截断处有省略标记，无 `|` 残文（问题 3）

* [ ] 主理人 plan/merge 的 system prompt 含记忆块（问题 4）

* [ ] 同一任务重跑更新旧条目而非追加（问题 5）

* [ ] 检索块仅在关键词 ≥2 且 FTS（trigram）有命中时注入；无关键词不触发（bm25 仅排序）

* [ ] 注入总字数 ≤3000（超限优先保核心块）

* [ ] 记忆超软上限（1000 条）时仅提示、不自动删除

* [ ] 迁移脚本对旧数据可重复执行，空条目已清理且留日志，正文含 `###` 子标题的条目未被误切

* [ ] 前端可编辑 / 置顶 / 删除单条记忆；置顶后进核心块
